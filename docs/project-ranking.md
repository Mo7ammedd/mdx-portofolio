# Personal-project ranking for the backend/platform CV

Reviewed 11 November 2026. This is a ranking of **evidence strength and value in this CV**, not repository popularity, recency, lines of code, or an assertion that lower-ranked work is trivial. Architecture, concurrency/consistency, failure handling, verification, independent implementation, operational maturity, and relevance were considered together. All entries remain personal, experimental, or academic; none is promoted to paid production experience.

## Ranking and selection

| Rank | Project | Strongest evidence | Verification and important limits | Decision |
| ---: | --- | --- | --- | --- |
| 1 | [LLMProxy](https://github.com/Mo7ammedd/LLMProxy) | Coherent domain/application/provider/persistence boundaries; atomic multi-scope Redis admission; transactional SQL allowance reservations; idempotent finalization; conservative restart recovery; failover before stream delivery. Ten provider adapters are present in the registry. | Pinned-head successful Actions run observed through MCP. Integration and recovery-drill implementation inspected. Fresh local restore was blocked by the host SDK; the alternative SDK image pull timed out before tests. No fresh local pass or external-provider billing guarantee. Concentrated history and no verified production scale. | **Selected.** Best personal example of backend architecture, distributed admission, accounting, and failure semantics. It adds financial/quota consistency rather than duplicating a deployment platform. |
| 2 | [LSMSharp](https://github.com/Mo7ammedd/LSMSharp) | Genuine storage internals: WAL, skip-list memtables, SSTables, Bloom filters, prefix encoding, GZip blocks, LRU caching, leveled merging, and recovery. Distinct from the professional control planes. | Original source failed integrity and new concurrency regressions. Local fixes use explicit-offset exact block reads and synchronize skip-list search/mutation. Four strict regression scenarios, the functional suite (200/200 integrity, 8/8 edge cases), and five repeated storage runs now pass. Engine build succeeds with four pre-existing nullable warnings. Small writes still precede WAL fsync; crash-safe manifest publication and arbitrary concurrent flush/compaction are not proven. Fix published as [e70fe08](https://github.com/Mo7ammedd/LSMSharp/commit/e70fe08fcd3cbbd16f7a83d7640a987f7c8d309f); the original audit snapshot predates it. | **Selected at your request after fixing the reproduced failures.** Storage depth complements backend accounting and networking. Experimental classification and durability limits remain explicit; no throughput or production-grade claim. |
| 3 | [AeroUDP](https://github.com/Mo7ammedd/AeroUDP) | Packet codec, handshake, sequence/ACK tracking, sliding windows, reordering, retransmission, congestion states, RTT estimation, and an asynchronous Tokio driver. This is a protocol implementation, not a UDP wrapper. | Fresh workspace run: 26 tests passed. Loopback/property/handshake coverage is bounded; no verified WAN performance, comprehensive hostile-network test matrix, protocol security, or production readiness. Generic author entries leave some attribution limits. | **Selected.** Strong complementary networking/concurrency depth. Explicitly experimental; retained for engineering strength, not age or layout convenience. |
| 4 | [GhostyKey](https://github.com/Mo7ammedd/GhostyKey) | Browser AES-GCM, fragment-only key transport, hashed capabilities, and SQL lifecycle functions that serialize consumption/expiry/deletion. The security and consistency boundary is narrow enough to inspect directly. | Fresh runs: 36 unit/API and 14 PostgreSQL tests passed. Twenty concurrent single-use readers yielded one successful consume; expiry is rechecked after lock waits. Browser E2E was not rerun; no security certification or production adoption. Dependency advisories remain maintenance work. | **Security-focused alternate.** Technically sound, but replaced by LSMSharp at your request after its local concurrency fixes and targeted validation, to emphasize storage internals. |
| 5 | [Disk-Mesh](https://github.com/Mo7ammedd/Disk-Mesh) | Chunked storage, checksums, replication scheduling, heartbeat failure detection, framed RPC, concurrent metadata access, and metadata snapshot replacement. | Fresh nine-scenario harness passed, including corrupt-replica failover, node-crash repair, concurrency, interrupted reads, and GC. Test nodes run within one JVM. Single master, periodic metadata snapshots, no consensus/WAL, and separate chunk/checksum writes limit stronger durability claims. | **Distributed-storage alternate.** The selected LSMSharp now supplies storage-engine internals; Disk-Mesh remains useful for a distributed-filesystem variant, with the single-master limits stated. |
| 6 | [cbox](https://github.com/Mo7ammedd/cbox) | Linux namespaces, native interop, cgroup controls, filesystem setup, capability dropping, PID-1 signal forwarding and child reaping in C#/.NET. | Integration/CI/release source inspected, not freshly run. Host capability requirements and isolation threat model remain unverified. No production-secure-container claim. | Strong systems alternate. Substantial overlap with professional Firecracker/runtime work makes it less additive in this version. |
| 7 | [apigo](https://github.com/Mo7ammedd/apigo) | OpenAPI/reference resolution, HTTP cancellation/redirect policy, SQLite state, local encrypted auth/history storage, package-contract and platform CI. Sensitive headers are stripped on cross-origin redirects; HTTPS downgrade is rejected. | Test/configuration source inspected, not freshly run. Local key-file storage has a bounded threat model; no verified adoption or production reliability result. | Useful developer-tools variant. Professional SDK/control-plane work already covers much of this signal. |
| 8 | [Aura Decor](https://github.com/Mo7ammedd/Aura-Decor) | Layered .NET commerce backend, order/cart ownership and payment flows, EF persistence, and integration boundaries. | Academic graduation product; no fresh suite execution or verified production operation. Shared work must remain collaborative. | Not selected because business-backend integration is already stronger in professional experience. Academic classification and graduation grade are preserved. |
| 9 | [HungerStation Microservices](https://github.com/Mo7ammedd/HungerStation_Microservices) | Separate .NET services, HTTP/API boundaries, Azure Service Bus consumers, and email/reward workflows. Consumers are implemented; they are not dismissed as uniformly unfinished. | Reward persistence catches/logs an exception and returns, allowing its caller to acknowledge after failed persistence. Database/broker actions do not establish an atomic outbox; duplicate handling and fault recovery are not proven. No formal suite run or production maturity established. | Not selected. Service count and broker use provide less convincing reliability evidence than the selected systems. |
| 10 | [SimuKernel](https://github.com/Mo7ammedd/SimuKernel) | MLFQ queue selection, quanta/demotion/aging, explicit simulated time, and LRU page-replacement modeling. | Educational simulation, not a real kernel, scheduler, hardware paging system, or actual runtime concurrency boundary. No meaningful automated suite established. | Preserved as educational depth in the portfolio/report; less relevant than the retained transport implementation. |

LLMProxy, LSMSharp, and AeroUDP are the final selected three: backend accounting/recovery, storage-engine internals, and networking/concurrency. GhostyKey remains a credible alternative for security-focused applications. The selection changed only after the reproduced LSMSharp failures were fixed and the targeted checks ran; the fix is published as commit e70fe08, without claiming a production release.

## Other discovered systems

Raptormind and ClincAI have substantial source, architecture, and lifecycle evidence, documented in the [ownership report](repository-ownership-report.md). Their personal versus employer/client classification is not established, so they are not silently relabeled as personal projects or added as jobs. The same rule applies to private commerce/agent applications and historical Oblien services. Forks receive no ownership credit for upstream implementation. Smaller application, exercise, and presentation repositories do not displace these candidates merely because they are newer or accessible.
