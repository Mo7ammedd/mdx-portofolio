### Openship

**Problem and architecture.** A self-hosted deployment/control platform for applications and supporting services. The monorepo separates contracts, a shared TypeScript platform/operation layer, persistence, runtime/transport adapters, and Hono API entry points. CLI, SDK, dashboard, desktop, and integrations consume the same platform behavior. Deployment targets include local hosts, SSH servers, and managed cloud workspaces. PostgreSQL and embedded PGlite serve different installation modes; those modes have deliberately different lock implementations.

**Engineering mechanisms and decisions.** `provision-lock.ts` combines a keyed in-process mutex with PostgreSQL session advisory locks. PGlite uses the single-process layer. This bounds same-process lock waiters instead of allocating a blocked database connection to every request. Recovery attempts both locks without waiting: a live worker must not be mistaken for an orphan after it eventually releases a lock. `deployment-recovery.ts` and `deployment.repo.ts` revalidate project, organization, deployment, and exact build-session identity under row locks. Recovery does not infer worker death from an old heartbeat alone or turn recovery time into billed execution time.

Managed-workspace admission persists command ownership. Unconfirmed remote exits retain the claim and require recovery before another operation changes that server. Rollback resolves a restore plan from the saved release, reuses frozen configuration, probes runtime state where supported, and compensates for failures after a runtime swap. This is explicit coordination between database state and external side effects, not a claim of a distributed ACID transaction. Managed edge publication is best-effort in the inspected rollback path; “zero downtime” or “failure-proof rollback” would overstate it.

**Security, persistence, and evolution.** Authorization resolves resource ownership and current membership, checks credential expiry/read-only scope, and restricts token grants to their actual capability. ### BytesMap

**Problem and architecture.** Database exploration, query composition, charts, reports, and telemetry. A TypeScript/Bun platform shares operations across transports and clients; database adapters separate external query engines from platform metadata. PostgreSQL/PGlite hold platform state. A separate Go event service admits telemetry through a durable NATS JetStream queue and indexes it into ClickHouse.

**Hard problems and decisions.** Query execution retains a connection lease across related reads so idle cleanup cannot close a pool or SSH tunnel during an active query. Row/byte/time limits and cancellation bound resource use. An extra result row establishes truncation; exact counts are opt-in because they can require expensive scans. This is a concrete cost/correctness tradeoff. Credentials use versioned AES-GCM envelopes with separate modern/legacy key handling; SSH transport and credential storage are distinct mechanisms.

Scheduled report claims and run records commit in one transaction. Claims include tenant, creator, definition, and principal identity. Report collection reauthorizes queries and sources, and delivery rechecks authority after a potentially slow export. Recovery marks an interrupted external workflow outcome unknown and pauses its schedule rather than risking duplicate side effects. These are bounded recovery semantics, not exactly-once delivery to arbitrary email/webhook systems.

The Go ingestion path applies producer scope, payload, retention, and quota policy before publication. Acceptance follows durable queue acknowledgement. The worker batches within configured size limits, inserts into storage before acknowledging queue messages, and negatively acknowledges failed batches for retry. Lost acknowledgements permit replay; queue/storage deduplication boundaries must not be advertised as universal exactly-once processing. Dataset deletion waits for pending accepted work before final purge.

**Testing and maturity.** Source includes database-backed recovery/tenant tests, producer/OTLP policy tests, storage integrations, browser acceptance, and packaged-runtime checks. CI configuration covers real database engines, Redis outage/reconnect, Go events/queue/ClickHouse, and release packaging. These suites were inspected, not rerun in this audit. Repository evolution spans initial August scaffolding, query/connectors/report work, platform evolution, and November ingestion/telemetry changes. Substantial work by other contributors makes **collaborative product ownership** the accurate classification; backend scope is much broader than an isolated reporting feature.

### LLMProxy

**Problem and architecture.** A .NET 10 multi-provider LLM gateway, separated into domain, application, persistence/rate limiting, provider adapters, and API/management boundaries. PostgreSQL plus Redis supports shared state; standalone SQLite/local-state mode has different operational properties. A runtime catalog freezes routing/pricing decisions for a request.

**Mechanisms and judgment.** Redis Lua checks all rate-limit scopes before consuming any and uses a shared cluster hash tag. Distributed dependency failure returns an unavailable error instead of silently bypassing shared limits. Conditional SQL updates reserve lifetime and monthly token/spend allowances in a transaction. Completion deletes/claims the reservation and updates usage in that same transaction, making duplicate finalizers idempotent. Fresh contexts are created for transaction retries. Abandoned reservations become conservatively estimated usage rather than allowing restart-based quota bypass.

Streaming failover fetches the first provider event inside the fallback boundary. Once output is delivered, a different provider does not replay the stream. Request cancellation does not cancel final bookkeeping; unsuccessful bookkeeping leaves a durable reservation for recovery. This cannot guarantee exactly-once billing by external providers, nor that estimated usage equals an upstream invoice. The CV describes local accounting and recovery mechanisms rather than those stronger claims.

**Testing and distribution.** Inspected integration tests cover PostgreSQL/SQLite concurrent reservations, duplicate finalization, Redis multi-instance rate/concurrency limits, and fail-closed dependency health. CI provisions PostgreSQL and Redis and runs recovery drills, container/SDK checks, security scanning, and distribution jobs. ### LSMSharp

**Mechanisms and limitations.** Writes enqueue WAL entries; batched flushes call `Flush(true)`. The inspected public revision does not establish crash-safe manifest publication, linearizable concurrent updates, or ACID transactions. Recovery skips some corrupt files, which is not equivalent to recovering all committed data.

This corroborates an unresolved correctness problem without proving its exact root cause. The inspected SSTable read path shares seek/read state; that is a concurrency concern, not a confirmed diagnosis. The local tree initially appeared modified; `git diff` established that all 29 changes were file-mode changes with zero text insertions/deletions. There is no local code fix that can be cited as resolving that recorded failure. A test called “Transaction Consistency” checks a final concurrent-update value; its name does not prove transactional semantics.
